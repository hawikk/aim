# Schema Versioning & Compatibility Policy — `ai-usage-event`

Status: v1.0 (proposed). Policy decisions on data retention and identity mapping remain with Security/Legal/CEO; this document covers schema mechanics only.

## Goals

- Collectors, ingest, storage, and dashboards must be able to ship independently without breaking each other.
- The metadata-only guarantee (no prompt/response text) must be enforceable at ingest, forever.

## Version scheme

- Versions are `MAJOR.MINOR` in the `schema_version` field of every event (e.g. `"1.0"`).
- Schema files live at `packages/schema/schema/v<MAJOR>/ai-usage-event.schema.json`.
- The schema declares a pattern (`^1\.[0-9]+$`) for the current major, not a pinned const, so minor bumps do not require a schema-file edit for producers.

## Within a major version (v1.x): additive-only

Permitted changes (minor bump: `1.0` → `1.1`):

- Adding a new **optional** field (or a field that is nullable / has a safe default).
- Adding a new enum value to a field consumers already treat as open-ended (see consumer rules below).
- Relaxing a constraint (e.g. widening `maxLength`, allowing `null` where previously required).

Forbidden without a major bump:

- Removing or renaming a field.
- Changing a field's type or narrowing a constraint.
- Making an optional field required.
- Changing the pseudonymization scheme of an existing field (`host_ref`, `user_ref`, `repo_ref`, `cwd_hash`) — that changes the meaning of stored data and is a major.

## Major versions (v2+)

- Published as a new schema file under `schema/v2/`.
- Ingest accepts **both** majors during a migration window of at least 90 days.
- Collectors may emit only one major per build; the platform never rewrites old events in place. Re-pseudonymization, if ever required, happens as a controlled, audited batch job producing new rows, never in-place mutation.

## Producer rules (collectors, proxy ingest)

1. Emit exactly the fields you have; optional fields are omitted or null, never guessed.
2. Set `schema_version` to the version the build was compiled against.
3. Never send fields outside the schema — ingest rejects the whole event (`additionalProperties: false`). A rejected event is counted and alerted on; it is not stored.

## Consumer rules (storage, dashboards, guardrail engine)

1. **Tolerant readers**: ignore unknown fields rather than failing. This is what makes additive minors safe.
2. Treat open-ended strings (`tool_raw`, `model`, `provider`, `detector`) as opaque; never switch on an exhaustive list.
3. `tool` values outside the sanctioned enum are already collapsed to `other` by producers; consumers must not expect new sanctioned values without a schema minor release note.

## Change process

1. PR against `packages/schema` with: schema diff, new/updated example events, and `validate.py` green.
2. Changelog entry in this file.
3. Review by platform owner + security (any field touching pseudonymization or `match_flags` also needs privacy review — it feeds the DPIA pack, AIM-29/AIM-43).
4. Dashboards/ingest updated **before** producers start emitting a new minor, or the additive rule guarantees safety regardless of order.

- **AIM-104 reconciliation note** (2026-07-22, no schema change): AIM-104 was scoped against the superseded network-event draft `schemas/event.v1.json`, which carried a `metrics` sub-object (`bytes_up/down`, `duration_ms`, `http_status`, `action`) without model/token fields. That draft is retired here — per `CANONICAL.md` it was never the live contract. In the canonical schema, `model`, `tokens_in`, and `tokens_out` have been **top-level optional fields since 1.0** (tokens: integer ≥ 0; `model`: nullable string ≤ 128 chars, required for `source=endpoint`). There is no `metrics` object; ingest rejects one via `additionalProperties: false`. **Consumer migration guidance:** dashboards/alerting read `model`/`tokens_in`/`tokens_out` from the event top level, treat absent/`null` as "unobservable at this source" (proxy events legitimately carry neither), and must not switch on exhaustive model lists (tolerant-reader rule 2). **AIM-100 coordination:** the inline-enforcement gateway must reuse these same top-level field names — no gateway-local `metrics` wrapper or alternate names; map OTel `gen_ai.usage.input_tokens`/`output_tokens` → `tokens_in`/`tokens_out` and `gen_ai.request.model` → `model` at the receiver.
